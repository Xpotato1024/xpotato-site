# 初稿品質ゲート：レビュー前に自分で防ぐ

更新紹介と工作・設定比較の編集で確定した判断を、初稿から使うためのチェック。[初稿制作workflow](first-draft-integrated-workflow.md)の各制作工程で確認する。完成原稿を長くするための追加項目ではない。公開記事を新規変更せず、次回の執筆・監査・限定修正に適用する。

## 使い方と判断順

1. 執筆前：読者、主題、各節の問い、証拠と図の役割を短く設計する（F01〜F04）。
2. 執筆・制作中：問いに必要な説明と実素材を揃え、重複を消す（F05〜F10）。
3. 初回提出前：原稿だけで追えるか、実表示と必要な導線が整ったか、範囲外を変えていないか確認する（F01〜F12）。

各確認は既存Jobのメモ/visual needs/監査findingに `満たす（対象箇所）/修正する/根拠不足/対象外（理由）` を短く残せばよい。専用の必須帳票、二重承認、追加の状態機械は作らない。担当stageの固定schemaと権限を広げず、別stageの実制作や配信を自己認定しない。

安全・事実の整合は残しながら、読者に不要な正確さの説明は減らす。判断を変える制約を削除して主張を強めない。重大な問題は提出前に修正し、趣味的な追加改善や無限リライトを完成条件にしない。

## 確認項目

| ID | 初稿で答える問い | 引っ掛かった場合の修正 |
|---|---|---|
| F01 | 初見の読者が対象・用途・今回読む理由と判断範囲を理解できるか | 推薦前に設計/材料と設定調整、旧問題/既存対策と新機能を分け、代替案と対象外を短く示す |
| F02 | リード・導入・各節が別の役割を持ち、更新の全体像があるか | 出来事と特徴説明を分担。代表例を深掘りしても他の主要変更は概要から落とさない |
| F03 | 補助概念が主題を奪わず、使う直前に理解できるか | 先に読者の問いと比較目的を置き、指標は表を読む直前等の必要位置で一言定義する |
| F04 | 問題→原因→従来対策→新しい解決→観測が同じ具体例でつながるか | 用語/設定/実装の羅列を避け、短縮で落ちた因果や比較対象を戻す |
| F05 | ヒーローがサムネイルでも記事の対象を識別させ、承認済み原本を保持したか | site palette/tokensとcrop安全領域を確認する。良いoriginal heroを本文の技術図で置き換えない |
| F06 | 症状の直後や初出用語の近くで、対応する実画像/モデルの見る場所が分かるか | 別名と部品を早く図で対応付ける。破断部/充填/トップ層は局所crop/zoomを優先し、全景が切れても比較の同一性は残す。枚数ノルマや挿入予定で済ませない |
| F07 | 動き・時刻・同一物体・比較条件を図から読み取れるか | 必要な離散時刻と方向を示す。原理の模式図と実現象の映像を分け、偽の中間状態や版比較を作らない |
| F08 | 図周辺と本文に同じ情報や操作説明を積んでいないか | 画像＋短い図題＋必要な出典に絞り、倍率等の重複を削除。再生操作はアイコン＋アクセシブルな名前 |
| F09 | 比較が成功条件を満たし、数字の条件・指標・解釈が同じ範囲か | 実測と説明用を分け、original evidenceと模式的破断を混同しない。速いが失敗する基準条件も残し、本文は小さな表/図と短い解釈、再現用寸法/方法はdocsへ |

| F11 | 依頼された完成形で実表示と発見経路を確認したか | スマホ/PCの図・数表・操作、検索別名、H1と対応schemaの検索titleを確認。一つのdescriptionが詳細/一覧/meta/OG/Twitter/WebPage・BlogPosting JSON-LDに一致するか実renderで照合する |
| F12 | 既に確定した良い点と変更対象外を保持したか | 指摘箇所と依存箇所だけ直す。保存版、承認範囲、実行結果を区別し、不要な再質問/再改稿を避ける |

## F03：定義は、主題でなく理解のための道具

「説明が必要」から「節の最初に置く」は導けない。まず、その節で読者が解決したい問いを一文で置き、用語/指標がその答えのどこで必要になるかを探す。

比較節の基本の読順：**比較する理由・対象と必要条件 → 指標の短い定義 → 表/グラフ → 結果の解釈**。

RTFを使う機能比較の例（編集用の例であり測定結果ではない）：

> 同じモデルで、接触予測と時間刻みを細かくする方法を比べました。描画を除く物理計算時間を測ります。
>
> RTFとは、シミュレーションが実時間の何倍の速さで進むかを表す指標です。
>
> ［比較表］
>
> ［この条件での差と、どちらを選ぶか］

RTFはこの節の主題ではなく表を読むための知識なので、比較の文脈を作ってから表の直前に置く。定義を離れた冒頭や表の後に置かない。

これはRTFだけ、または常に「表直前」だけの規則ではない。P95、消費電力量、精度指標、3Dプリンタの流量等でも同じ判断をする。

- **指標自体が主題**（「RTFとは何か」）なら、定義から始めてよい。
- 表より前の文で指標を理解しないと読めないなら、その初使用位置で説明する。未定義のまま表まで引き延ばさない。
- 読者が既知、または前の節で説明済みなら、再定義せず必要な参照だけにする。
- 初見読者に必要な背景は省かない。「定義を遅らせる」ことを目的化しない。

## F07・F08：理解を助ける図で止める

動きの説明には原因の前後が見える時刻を選ぶ。0/20/40/60 msで20〜40 msの間に壁を置く例は一例であり、全GIFへ同じ時刻/配置を固定しない。状態や試行条件を変更した場合は正しく再計測し、ラベルだけ変えない。

ストロボは離散判定の原理、native描画のGIFは実際の現象を示す。両方が別の疑問を解くなら併用し、同じことの反復なら減らす。過去の球を現在の球と同じ濃さで増やすだけの図は、複数物体に誤読される。

図内の「0.6倍速」「左右の対応」「時刻」が読めるなら、それを本文や補足欄へ再掲しない。説明文を図下から本文へ移すだけでは改善ではない。必要な解釈だけを本文に残し、重複は削除する。altは非視覚利用の代替であり、可視の重複削除を理由に消さない。

## 実行可能な題材は、再利用できる元データから作る

モデル・シミュレーション・スライス結果の制作が依頼されている場合、主成果物は再利用できる元データと実出力であり、見た目が似た生成画像ではない。画面風の画像を作って「記事用素材を制作した」と完了しない。

例えば3Dプリントの構造を説明するなら、寸法を変更できるCADソースとSTEP/STLを作り、同じモデルを実スライサーで条件だけ変えて処理する。設定・3MF・G-codeを保存し、その出力から図を取得する。シミュレーションならモデル・条件・保存stateから描画する。同じ作法を対象ごとに選ぶ。

画像生成は意匠・概念・装飾が目的で認められた場合だけの選択肢であり、上記の工学的な元データ制作の代替にしない。生成画像の見かけの外周本数・充填率・層数を実結果として扱わない。

再読込して同じ条件を再現できるか、出力の設定と実際の経路/状態が対応するかを確認する。ソフトの版、入力、設定、出力と図の対応を記録し、再生成方法と安全な共有物を用意する。実機へ適合しない参考G-code等をそのまま運用可能としない。

実データを別のビューアで立体表示する場合は、その事実を短く示し、元ソフトの画面キャプチャや実印刷と偽らない。断面表示・途中層の非表示は表示上の変更として記録し、モデルを変更した比較と混同しない。資料の画像を増やすだけでなく、作成物をユーザーが再利用できることまで完成条件に含める。

## 本文は、制作報告ではなく理解の案内にする

実データを作って検証する必要と、その制作過程・詳細条件を本文に書く必要は別。本文には「何と何を比べるか」「図が何を示すか」「そこから何が分かるか」を置く。再現だけに必要な試験片の寸法、ノズル径、ソフト版、表示高さ、画像の切出し操作等は、元データ・設定・README・方法資料へ残す。既にそこにある情報を本文や図下へ再掲しない。

例えば「48×32×8mmの試験片を作り、内部が見えるよう高さ4mmまで表示した」ではなく、「同じモデルの断面で、外周だけを増やした場合と、充填率だけを上げた場合を比べます」とする。必要なのは操作の実況より、読者が見ている結果と比較の目的である。

数値を一律に削除する規則ではない。変更条件の外周数/充填率、層数と厚さの関係を説明する積層ピッチ、結果の解釈や安全性を変える条件は必要な位置へ残す。図にある値の重複は消しても、何を変えた比較かを曖昧にしない。

著者が画像を作るために行った処理と、読者が目的を達成するための操作手順も区別する。前者は結果の記述へ置換し、後者が記事の目的に必要なら保持する。制作手順そのものが主題のチュートリアルや、条件が結論を左右する実験報告では必要な手順・条件を省略しない。

## F09：根拠は厚く、本文は小さく

比較目的と成功条件を先に決め、同じモデル/機器/版/入力/計測区間で基準・新機能・従来の対策を比べる。成功する条件を測定後に都合よく定義しない。入力・条件の調整をしたら、全比較へ同様に適用して根拠に残す。

指標の分子/分母・単位・良い方向・機器・版・warmup・反復・集計方法・計測に含む範囲を根拠記録へ。本文は理解や結論を変える情報だけに絞る。RTFの「native物理だけ」と「描画/通信を含む全体」を混同しない。

最速だがすり抜ける等の失敗条件を成功例と同列に推薦しない。新手法の負荷・不利益も残し、「この例で」を一般的な保証へ広げない。既存の汎用機能で計測/描画し、記事専用の物理実装を研究基盤へ混ぜない。

## フィードバックを減らすための運用

完成基準は、ユーザーが了承した更新紹介・工作記事で確認された編集上の判断。文字列、図の枚数、機器、具体的なRTF値を他記事へコピーするテンプレートではない。本文の承認はpublication/merge権限を自動付与しない。

既存のJob/PRに、再発した原因のID、修正範囲、初稿前に防げたかを必要な分だけ記録する。新しいユーザー要求、単なる保存/配備回数、既存方針の取りこぼしを分ける。**Siteのv11という保存版番号を、そのまま11回のFBや効果測定の分母にしない。**

スキル更新では旧ルールの置換まで行い、矛盾した追記を蓄積しない。e.g. 旧「題/説明/補足/出典を全部積む」は現行の基本形ではなく、caption/note属性が使えることも執筆義務を意味しない。

自己点検は既知の問題をユーザーへ出す前に止めるためのもの。semantic stageや独立監査のscope/固定requestは維持する。チェック表の埋まり、自動testのPASS、モデル評価の正解を、実際の読者理解やFB削減の実証とは呼ばない。
