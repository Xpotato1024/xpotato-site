# 具体例・補足・図の編集判断

2026-10-28の原稿へのフィードバックを反映。自然な日本語・図版規則と合わせて使う。禁止語や最低枚数ではなく、読者が対象を見分け、次の判断をできるかで判定する。

## 先に具体物を選ぶ

抽象的な定義を並べてから例を探さない。執筆前に、主要な説明を支える実物・ソフト・設定・操作・症状を選ぶ。例を一貫して使い、途中で無関係な例へ飛ばない。
「スライサーは…」なら、対象読者が触れるBambu StudioやUltiMaker Curaを挙げ、何をするソフトかをその場で説明する。固有名詞を増やすだけで具体的になったと判定しない。名称・UI表記・設定の分類は公式資料や固定版のソースで確認する。
主要な判断には、対象、変えるもの、変えないもの、見る箇所を用意する。外周数2→4と充填率15%→30%は別々に比較し、両方同時に変えて原因を断定しない。数値例は試すための設定例であり、未実測の推奨値・強度保証・改善率ではない。
各H2/H3に必ず一例、各章一枚といったノルマは設けない。短い補足は統合できる。重要な説明に具体物・観察対象がない場合は書き直す。

## 問いかけと本文の語調

短い疑問見出し・タイトルは「充填率100%なら丈夫になる？」「どこを変える？」のような常体を基本候補にする。本文のです・ます調と併用してよい。敬体統一を理由に「丈夫になりますか？」へ直さない。
読者への依頼や操作指示は丁寧に書ける。説明文まで不規則に常体へ変えたり、一定間隔で語尾を変えたりしない。読者の誤解・経験を推測した「〜と思っていませんか？」は、疑問そのものへ戻す。

## 補足の置き場所

補足ごとに「これがないと読者の判断・操作はどう変わるか」を確かめる。
- 判断を変える条件、操作直前の危険：該当する本文・手順の近くに短く残す。重大な安全条件を脚注へ隠さない。
- 根拠の詳細、版の差、例示の条件、図の由来：必要な一度だけ、キャプション・脚注・記事末の資料欄へ置く。
- 既出の注意、関係の薄い例外、結論に影響しない自己弁護：削除する。
主張を広げて大量の免責を後置するのでなく、最初から対象に合う範囲の言い方にする。「必ず」「万能」へ強めて補足を削ることもしない。
「場合があります」「条件によります」は説明の代わりにしない。分かる条件は具体的に書き、同じ留保を段落ごとに繰り返さない。
図すべてに長い免責を付けない。「模式図」「設定比較の例」など役割を一度示し、必要な意味はラベルや凡例で伝える。

## ヒーロー・導入画像と説明図

手段の順位を全用途に固定しない。
- ヒーローや導入：題材と作業場面を伝える実写真、またはImageGenの編集用イメージ。許可済みで生成可能なら制作する。貧弱な線画を「図だから正確」として代用しない。
- 正確な関係・比較・力・寸法：SVG、CAD等の決定的描画、または実写真への正確な注釈。技術記事の全画像をSVGにする規則ではない。
- 操作の場所：取得した実スクリーンショット。生成した画面を実UIとして紹介しない。
- 実測や破損の証拠：実際のデータ・写真。概念画像を証拠に流用しない。
製品識別が理解を助けるときは、公式のロゴ・アイコンを取得し、原本を変形・再描画させず使う。ImageGenの背景へ原本を後合成するか、隣に正確に配置する。ロゴ・設定名・数値・UIの正確さを生成モデルに任せない。
生成背景と公式アイコンの合成は編集用導入画像であり、実ソフト画面・メーカー広告・推奨関係と誤認させない。キャプションで短く区別し、出典・取得版・ライセンス等は素材記録に分ける。コードのOSSライセンスを商標利用許諾と同一視しない。
全製品への画像を義務化しない。ただし依頼で指定された素材を省くなら理由と代案を記事外に示す。

## 図を説明として成立させる

描画前に、その図を見て答えられる問いを一つ決める。完成後は実物で確認する。
1. 対象が分かる。箱・フック・試験片等の輪郭を描き、意味のない長方形の縞だけにしない。
2. 名称・方向・比較軸が図から追える。外周/インフィル、荷重、固定部、積層方向、割れる面など必要なラベルを残す。
3. 比較では外形・視点・荷重等の固定条件をそろえ、変更点を一目で示す。
4. 全キャプションを読まないと対応が分からない状態を避ける。長い説明は本文へ、短い識別ラベルは図中へ置く。
5. スマホ実幅で文字が読める。横長比較を縮めて済ませず、縦配置・分割・HTMLラベルを選ぶ。ラベルを全削除して問題を隠さない。
6. 矢印・破断・寸法が本文と矛盾しない。美しさを正確さの証拠にしない。
SVGの文字を画像化する場合は日本語グリフと書体を実際に確認する。既存のフォント設計を尊重し、フォントファイルを配布しない。

## 納品前の確認

読者として一度読み、抽象評価だけの段落、注意の反復、説明できていない図、実行できない手順を直す。
想定読者・読む場面・数値例の条件・図の役割・未確認事項は記事外の編集メモに分ける。本文へ作業報告や監査リストを混ぜない。
公開・実測・権限の境界は既存規則どおり。自己点検を独立監査や読者評価のPASSと呼ばない。
