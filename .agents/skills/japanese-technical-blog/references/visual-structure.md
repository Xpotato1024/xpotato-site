# 読者の認知負荷を減らす記事構造・図版の設計

この資料は執筆判断用。公開記事へチェックリストをそのまま転記しない。
規範となる編集方針は docs/content/editorial-policy.md、MDXの許可構文は docs/contracts/content-module-contract.md。

## 読者が「いつ」「何のために」読むか

毎回、読む状況を1つ選ぶ: 作業中に答えを探す / 印刷や実装の直前に確認する / 比較して選ぶ / 仕組みを学ぶ / 検証内容を追う。
前提知識、知りたい判断、読後にできることを1文ずつ仮置きする。
本文の最初の画面で、読者が対象・答えの方向性・読む価値をつかめるようにする。
説明は初心者へ過剰に、経験者へ不足なくではなく、対象読者が実際に必要とする量を選ぶ。

## 流し読みで分かる意味構造

- 見出しだけを縦に追い、問い→判断→仕組み→適用条件が分かるか確認。
- 同じ深さの見出しは同格の問い・役割にそろえ、h2/h3を飾りとして使わない。
- 連続する3文以上が「条件A・対処A・理由A」のように反復するなら、箇条書き・表・DiagnosticListを検討。
- 手順には順序と確認結果が重要なので番号付きリストまたはSteps/Stepを使う。
- 条件・判断の分岐には比較表、診断リスト、または判断フローを使う。
- 図表が結論を直接表す場合、前後の文章で全内容を言い直さない。要点と条件だけ説明する。
- 記号やSVGアイコンだけで内容を表さず、テキストの見出し・ラベルを残す。

## 図版が減らす「読者による脳内補完」

本文の下書き時に、読者が次を自分で想像する必要がある箇所に印をつける。

1. 空間関係: 中身の断面、部品位置、接続、荷重方向 → SVG模式図/実写真。
2. 時間・操作の順序: 画面遷移、組立前後、処理の流れ → 手順図/元スクリーンショット。
3. 数量・比較: 各条件の差、傾向、ばらつき → 元データによるグラフ/比較表。
4. 原因・条件分岐: 症状から疑う箇所への関係 → 診断リスト/フローチャート。
5. 外見と質感: 積層痕、破断面、配線の状態 → ユーザー提供の実物写真。

図が理解の負荷を減らせるかで採否を決める。図数の最低基準、段落ごとの画像義務は設けない。
一つの高密度な図を一度に読ませるより、必要に応じて意味ごとに図を分割する。
逆に、本文を読まなくても凡例やラベルから結論が読み取れる図は過剰説明を削れる。

## 素材制作方式の選び分け

| 用途 | 第一候補 | 境界 |
| --- | --- | --- |
| 断面、寸法、配線、荷重、操作の分岐 | SVG / 決定的描画 | 幾何学・ラベル・矢印の正確さが必要。精密な事実を生成画像に推測させない |
| 実際の画面、印刷結果、失敗や破損状態 | ユーザー提供の写真・画面写真 | 未提供の実物を描画して観測結果に見せない。権利とプライバシーを確認 |
| 数値・性能・確率・比較 | 出典・実測から生成する図表 | 数値や散布点を補作しない。条件・単位・サンプル数を明示 |
| 抽象的な概念や雰囲気の説明、アイキャッチ | ImageGen | 概念図/イメージと分かる形で。原理・事実・実験の証拠と混同しない |
| 言語化で十分な単純条件 | 文章・リスト | 画像は追加しない |

ImageGenの使用はモデルに対する画像依頼・承認条件を満たす場合のみ。外部providerへのprivate input送信には別のdisclosure承認が必要。
実写の再撮影/画像取得に承認が必要な場合は先に確認し、未取得の素材があることを成果物に記録する。

## 作成・挿入と作成できない場合の扱い

完全な記事成果物が依頼され、必要な根拠と制作手段があるなら、判断した図版を実際にSVG/データ可視化/許可された生成画像として作り、該当する説明の近くに配置する。
記事を短くする代わりに、図へ意味関係を移す場合は図中に必要な用語・凡例・矢印を付け、本文側でその関係を確認できる説明を残す。
現物写真がなければ写真風の合成で埋めず、撮影依頼と写真なしで伝えられる範囲を記事外に示す。
Article JobのAI draft段階はvisual needs proposal、visual planner段階は制作方式と論理assetの計画まで。実体の生成・Media Registry登録・公開は承認済みの後続工程に委譲し、Skill内の「作成」の指示で権限を広げない。

## 写真を追加で求める条件

写真が説明・再現性・証拠に必要で、既存提供物で代用できないときだけ具体的に依頼する。

- 何を示すためか（例: 層間破断か材料自体の破断か）
- 被写体、向き、距離、枚数、必要なら寸法基準/照明
- 撮影前後で合わせてほしい条件と、個人情報/位置情報の除去
- 必須か任意か、撮れない場合は何を本文で限定するか

「写真を何枚かください」で止めない。撮影済みの素材をまず確認し、再撮影要求を最小限にする。

## 図と本文の結び付け

- 図は、それが説明する段落や判断の直後・直前へ置く。
- 「下図の青い部分」のような色だけの指示を避け、名称と位置で指す。
- captionは何が分かる図かを説明し、altは図を見られない読者に必要な情報を渡す。
- 単なる装飾アイコンはaria-hidden。ラベル・図の意味は文章に残す。
- モバイル320/390px、デスクトップ、200%拡大を想定し、ラベルや矢印が詰まらないか確認する。
- 外部媒体と論理media IDは切り分け、MDXで保存先の直接URLを指定しない。

## サイトの構造化部品

通常の文章・箇条書きはMarkdownを優先し、意味構造が増える場合だけ許可済みのcontent moduleを利用する。

- 注意/補足にはCallout。一般論を装飾のために囲まない。
- 操作手順にはSteps/Step。独立した選択肢は手順に偽装しない。
- 症状→最初の確認→理由が反復する場合はDiagnosticList/DiagnosticItem。比較評価軸に沿うものは普通の表でよい。
- 診断の「確認」は候補であり、実測で確定していなければ原因と断定しない。

使い方の例:

~~~mdx
<DiagnosticList>
  <DiagnosticItem symptom="曲げると折れる" check="割れた場所が根元か、部品の途中かを確認します。" action="外周、根元の形状、造形方向を別々に検討します。" />
  <DiagnosticItem symptom="上から押すとへこむ" check="へこむのは上面だけか、部品全体かを区別します。" action="上面の厚さと、内部の支えの配置を確認します。" />
  <DiagnosticItem symptom="層の境目で割れる" check="割れ目と積層方向を対応させます。" action="造形方向、印刷温度、冷却条件を確認します。" />
</DiagnosticList>
~~~

属性は文字列リテラルのみ。実行時のJavaScript props、任意CSS class、独自SVG注入は禁止。
アイコンはサイト共通部品が意味に応じて表示する。内容を説明する小図は別の素材として計画し、構造アイコンを説明図の完成数に含めない。

## 文体: 親しみやすいが、精度を落とさない

[natural-japanese.md](natural-japanese.md)を使う。短い節は独立性と説明の完結性で判定する。画像の未準備で重要な説明が欠けている場合、完成扱いしない。

- 自然な疑問文、簡単な具体例、「まずここを見ましょう」などの行動が分かる表現を選ぶ。
- 初出の専門語が不要なら日常語に置き換え、必要なら短い説明を添える。
- 用語を言い換える前後で物理的意味を保つ。応力・力・モーメントは別の量。専門語が必要なら残して定義し、矢印や模式図で関係を補う。
- 主観的な盛り上げ、過度な比喩、読者への馴れ馴れしさ、根拠のない断定は避ける。
- 視覚素材と本文を一組の説明として推敲し、同じ情報を長文で二重に説明しない。

## 表示と内容を固定した検証

CSS比較では同一MDX・図版・出典を使う。原稿を改稿した場合は内容変更として別に差分を示し、短縮したサンプルを同じ記事と呼ばない。正式なContentLayout・目次生成・Media Registry・フォント処理を通したprivate candidateを使う。図中文字は実際の320/390px表示で判読し、横はみ出しゼロだけで合格にしない。日本語メタデータの実使用フォントと欠字も確認する。

## 出力とセルフチェック

記事に加え、必要時は編集メモで「想定読者・読む場面・図に置き換えた説明・選定媒体・未撮影の写真要件」を開示。
不必要な大量の画像やcallout、本文内の編集メモは禁止。
見出しだけの流し読み、図だけの流し読み、文字だけの流し読みの3通りで内容の破綻を確認する。
