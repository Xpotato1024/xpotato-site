# 読者起点の更新紹介：v11で確定した編集基準

更新紹介・試用比較を、開発者の作業報告ではなく初見読者への案内として作る。[初稿品質ゲート](first-draft-quality-gate.md)を共通の確認入口とする。下記はその用途別詳細であり、固定の章数/字数/図数ではない。

## 1. 対象・更新・全体像を伝える

読者は著者の利用歴やこの会話を共有していない。用途、何が公開されたか、何を確かめる記事かをリードで示す。導入節では無料/ライセンス、特徴、開発元、確認できる採用例と分野での位置づけへ進め、同じ定義を言い換えて繰り返さない。

「約3年ぶりの4.0」ではなく「約3年ぶりのメジャーアップデートとなる4.0」のように修飾先を保つ。title/description/card/OGも同じ意味にする。

更新全体を短く俯瞰し、重要で分かりやすい代表例を深掘りする。作れたGIFが2種類だからといって主要変更も2つだけにしない。新登場、改善・正式化、前メジャー以降の累積変更を分け、公開日と前版の日付は一次資料で確認する。

普及度は根拠が支持する分野で明確に述べる。引用数、利用論文数、DL数、実利用シェアは別。古い単時点の引用数から現在の差の拡大や全分野の唯一の標準を断定しない。企業製品群と個別製品も混同しない。本文は採用例と位置づけを一文程度に絞り、統計の母集団/時点は根拠記録へ。

## 2. 具体例を、問題から改善まで使い続ける

候補となる流れは、用途/全体像 → 従来の問題 → 原因 → 従来対策と負担 → 新しい解決 → 同じ例の実比較 → その他の変更 → 試し方/更新 → 観測に基づく結び。

一つの現象を節の途中で別の例へ置き換えない。機能名、数値設定、repoディレクトリ、保存形式から始めず、「何が困ったか」「どう変わったか」をつなぐ。内部API、commit、worktree、詳細ログは必要な再現資料へ分離する。

補助概念を説明する順序は[初稿品質ゲートF03](first-draft-quality-gate.md#f03定義は主題でなく理解のための道具)に従う。比較目的→必要条件→指標の短い定義→表→判断を基本にし、指標自体が主題なら定義から始める。RTFは配置判断の例で、すべての比較に使う指標ではない。

## 3. 本文と画像を同時に設計する

識別・用途・空間・時間・比較・操作のどこで読者の脳内補完を減らせるかを先に決める。画像は積極的に用いるが、無関係な写真で「1節1枚」を埋めない。図数ノルマがないことを理由に必要な画像を省略しない。

組織の初出には公式の記号/文字ロゴ、ロボット等の用途には実写真または正確なモデル画像、UIには取得した実画面を検討する。同じ名称ごとにロゴを繰り返さない。権利・出典・取得時点・hashは素材記録へ。

公式ロゴは原本の形・色・比率を保ち、想像で記号を作り直さない。公式に置かれていることと自由な転載許可は別。組合せや配置で著者・スポンサー・推奨関係を誤認させない。生成した情景・UI・ベンチマークを実物/実測と偽らない。

## 4. ヒーローは小さくても主題を識別できるものにする

本文と無関係でないだけでは足りない。200〜400px程度の一覧カードで何の製品/テーマの記事か分かるかを確認する。一般的な人型だけでロボット/製品が伝わらないなら、権利確認済みの四脚/アーム等の実モデルと正確な製品名の組版を検討する。

四脚は今回の選択例であり全記事の指定ではない。主役より大きい床/空の余白、切れた足先や文字を避ける。取得したロゴと生成背景は分け、正確な名前や版は決定的に配置する。

hero、一覧、分類/タグ、OG/Twitter/JSON-LD、altが同じ対象と版を参照するよう担当工程で同期する。PC・狭幅・各crop比率で確認する。

## 5. 時系列を複数物体に誤読させない

動きの図には、進行方向・時刻・同じ物体の対応をそろえる。現在と過去の物体を同じ濃さで置くだけにせず、現在の実体、過去の目盛り/輪郭/ラベルを見分けられるようにする。色だけを手掛かりにしない。

原因の前後を読むのに2時刻で足りなければ、前・直前・直後・後の離散時刻を選ぶ。例えば0/20/40/60 msで20〜40 msの間の壁通過を示す。これは全記事への固定時刻ではない。配置や初期条件を変えるなら同条件で再実行し、旧結果のラベルだけを変えない。

観測したstate以外を実測の中間姿勢として補間しない。模式図の矢印は説明用の対応線であり実接触の観測ではない。物体の輪郭を拡大して、止まった球が壁に重なるような図にも注意する。

## 6. 原理の図と実現象の映像を使い分ける

ストロボは離散判定の原理、native描画のGIFは実際にすり抜ける/抑える現象を示す。両方に役割があれば併置する。同じ情報の反復なら削減する。

比較はカメラ・形状・初期値・入力・時間刻み等の固定条件と変更点を対応させる。OFF/ONや弾性/弾塑性を旧版/新版と呼ばない。版比較は実際に双方の環境で得た根拠だけを使う。

柔軟体の変形は衝突前・接触中・解放後を区別し、残留形状が読める終端を保持する。ループのリセットを弾性復元と誤読させず、逆再生や別の物理計算で挙動を作らない。保存済みstate、再生速度、保持時間、加工履歴を制作記録へ。

通常の汎用Scene/Trial/描画を再利用し、記事専用の物理solverや例外経路を研究基盤へ増やさない。計算/画像を作成できる依頼なら素材まで完成し、挿入予定の文だけで止めない。

## 7. 図周辺は少なくする

基本は**画像＋必要なら短い図題＋必要最小限の出典**。何を見るか・結果の意味は本文へ一度置く。図下へ題名・説明・補足・自作クレジットを毎回積まない。caption/noteの実装があることを執筆時の入力義務にしない。

図内の速度・時刻・左右の対応を本文へ繰り返さない。「補足を本文に移す」の前に重複を削る。自作図の来歴は記事末など一度、第三者の必要な権利表示・出典は残す。

補足は原則省き、判断を変える条件だけを主張の近くへ自然に含める。正確さを演出する注記や制作手順は記事外へ分離する。分かりやすさを優先しても結果・条件・出典を偽らない。

再生操作は画像に隣接する一時停止/再生アイコンだけ。「再生・停止できます」等の可視説明を足さない。aria-label、状態、focus、44px以上を目安にした操作領域、reduced-motion時の静止表示は維持する。

GIFが動画より軽いと決めつけず同じ元フレームのサイズと品質を確認する。要求されたGIFを黙って動画へ置換しない。既存media契約、正規保存/公開境界を守る。

## 8. 比較・使い方・結びを主題へ戻す

定量比較は[初稿品質ゲートF09](first-draft-quality-gate.md#f09根拠は厚く本文は小さく)で測定範囲と成功条件を確認する。正文は小さな表/図と短い解釈で十分ならそこで止め、原稿全体をベンチマーク報告へ変えない。

未利用者に試す入口、既存利用者に対象版・要件・互換性を示す。旧環境の保全→更新→版/依存/既存モデルの確認をつなぎ、アンインストール等の作用範囲は実行前に示す。コピー可能なコマンドを画像だけにしない。

比較・試用をした記事では、中心の問いへの答えと、観測に基づく使いどころ/次の確認で短く締める。「いかがでしたか」や全節再掲だけにしない。未経験の実機・長期運用や著者の感情をオリジナリティとして創作しない。

## 9. 完成形を確認して渡す

実際の原稿・図・ラベル・表を同じ画面で見て、先頭/中間/終端、モバイル/PCの大きさ、数表と操作を確認する。画像存在・横はみ出しゼロだけで理解しやすさを実証したとは言わない。

依頼が完成記事なら一覧/分類/タグ/SEOと正規のレビュー表示まで担当経路へ渡す。既存本人限定Siteの更新が認可されている場合は同じSiteへ反映し、保存版と結果を確認する。ローカルbuild、レビューSite、本番公開、人間の承認はそれぞれ別。

承認されたv11から学ぶのはこの判断過程であり、永久に同じ題材・字数・図数・RTFを選ぶことではない。後から矛盾する指示を重ねず、[F01〜F12](first-draft-quality-gate.md)へ戻って初稿段階で確認する。
