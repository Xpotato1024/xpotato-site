# 読める実装と責務の分離

## 情報を置く場所

| 場所 | 主に答える問い | 書く内容 |
| --- | --- | --- |
| コード | How | 型、名前、制御フローで実際の処理を明示する |
| テスト | What | 入力・操作に対して保証する振る舞い、不変条件、拒否と回復 |
| コミット | Why | 変更が必要だった事情、選択理由、影響範囲と重要な代替案 |
| コードコメント | Why not | 素直に見える代案では壊れる条件、意図的な制約、解除条件 |

これは主な役割であり、厳格な排他分類ではない。公開APIの単位・副作用・所有権・前提は型や短いJSDocで説明する。長期に有効な横断判断は既存ADR/contractへ置き、コミット履歴だけを探させない。コメントは現行コードに密着した理由だけを持ち、仕様の第二正本にしない。

## 整形

正本はrootの `prettier.config.mjs` と `.prettierignore`。通常の手書きTS/JS/TSX/Astro/CSSとworkflowを同じ固定formatterで処理する。

```sh
npm run format
npm run format:check
```

100文字のprintWidthは折返しの目安で、長いURL・SVGパス・正規表現・意味を持つ文字列を壊して守る上限ではない。インデント2、LF、末尾改行を使う。複数の副作用や宣言を一行へ詰めない。新規/改修する分岐は原則ブレースを使い、例外処理・状態変更の単位を視覚的に分ける。

本文MDX、署名済み/承認済みデータ、生成物、immutable vendor、フォント生成CSSは対象外。除外は用途で説明し、整形エラーを隠すために広げない。埋め込み文字列はfixtureや配布byteを表すことがあるため自動整形しない。自作の実行コードを文字列へ入れる必要がある場合も、テンプレート内で読みやすく改行する。

固定配布物のハッシュで権限を限定するfont preparerとinstaller所有のラッパーは、生成・承認契約に従うため整形から除外する。古いコードへの互換aliasを増やす理由にはしない。

公開用の小さなJavaScriptもソースは整形する。`ops/build/public-scripts.mjs`で配信時だけ空白を圧縮し、従来の転送量上限・実成果物の検証を維持する。開発ソースの行数削減や性能上限の緩和で代替しない。

`format:check`は既存source preflight内で実行する。専用workflow・独自formatter・整形のための証跡DBを作らない。整形はテストや型検査の代わりではない。

## 分割する条件

行数やファイル数ではなく、変更理由・状態の寿命・副作用/認可境界で分ける。

- UIは画面の組立て、featureは利用者の操作、hookはまとまった状態とその寿命を所有する。
- IOは保存/通信adapterに置く。競合解決等の判断は可能な範囲で純粋関数にし、表示を持たせない。
- API入口は認証・CSRF・エラー応答を見通せる形で保ち、認証済みの業務操作だけを各domainのhandlerへ渡す。
- local featureの概念を、再利用実績なしにsharedや汎用managerへ引き上げない。長さを減らすだけの一行wrapper、巨大なcontroller引数、循環依存を作らない。
- 移動後は全呼出元を直し、旧pathの再export/stubを残さない。内部だけで使う型を無意味なtypes.tsへ移さない。
- CSSは同じ責務の近くへ置く。共通値はdesign-systemを参照し、機械的な分割でcascade順を変えない。

一つの関数を分割すると状態や順序がかえって追いにくくなる場合は、そのまま読みやすく保つ。行数制限やuseState数の達成を目的化しない。

## コメント

コードを日本語へ翻訳しただけの説明、変更日時の列挙、実装済み内容の宣伝、コメントアウトした旧コードは残さない。

有用な例:

```ts
// 保存中にも入力できるため、サーバーの完了通知で最新の本文を置き換えない。
const updated = mergeGitSaveResult(currentDraft, submittedDraft, commit);
```

```ts
// Webhookはブラウザsessionではなく署名で検証する。CSRF経路へ混ぜない。
return await acceptGitHubActivity(request, env, now());
```

認可・競合・削除・復旧の意外な制約には、その場で必要な理由を記す。長い背景はADR/Issueへの参照と解除条件を添える。TODOには具体的な不足/条件か追跡先を付ける。コメントと挙動が食い違えばコード/テスト/契約を確認して修正し、コメントの存在を正しさの証拠にしない。

## テストとコミット

テスト名は利用者または呼出側が観測する仕様を述べる。実装の空白・一時変数・privateメソッド数を固定しない。失敗系・非同期競合・権限拒否・保存失敗を、入力と結果で確認する。成果物byte、SQL、CSP、署名対象など、byte自体が契約である場合は完全一致を維持する。

コミット件名は何を変えたか、本文はなぜ必要だったか・何を守ったかを述べる。整形と責務変更は別コミットにする。大規模な整形commitは `.git-blame-ignore-revs` に記録し、`git blame --ignore-revs-file .git-blame-ignore-revs -- <path>` で意味のある履歴を追えるようにする。履歴を書き換えたり利用者のglobal Git設定を変更しない。

## レビュー観点

コードから処理順・副作用・失敗時の状態を追えるか、テストが守る仕様を表すか、変更理由が履歴に残るか、意外な制約の理由が該当箇所で分かるかを確認する。formatter成功や行数減少だけで保守性改善を完了と扱わない。
