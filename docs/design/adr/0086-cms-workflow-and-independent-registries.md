# ADR-0086: CMSの作業開始と記事に依存しない管理

## 背景

執筆用の一画面に機能を追加してきたため、原稿やブランチを選ぶ操作と本文編集中の操作が混在していた。タグや空の連載を作るためにも記事を開く構造は、実際の記事制作の順序に合わない。モバイルでは上下の操作領域に加えてソフトウェアキーボードが本文を隠し、viewportを縮めるだけではグループ内の入力位置が見えるとは限らなかった。

## 実装候補

ホームから「新規作成」「既存記事を改稿」「下書きの続き」へ分岐する。原稿の検索・種別・添削から開くかどうかと、作業場所を選んでから編集画面へ入る。Gitは取得したcommitからの`content/*`作成か既存作業ブランチを選び、未接続でも端末だけで作業できる。公開原稿の改稿は同じContentIdの下書きで扱う。

分類・タグ・連載は記事とは独立した画面・状態にする。IndexedDB version 3に`workspace` storeを追加し、管理の基準manifest・未保存変更・作業ブランチを保持する。ホームや管理の利用だけで空の記事を保存しない。既存の本文・画像・添削・履歴storeは維持する。

`/registry/save`と`/registry/pull-request`を既存のowner認証・CSRF経路へ加える。記事sourceや任意pathを受けず、許可された分類追加・連載変更のみを扱う。保存は`expectedHead`と非force更新、連載の基準値照合とContentId参照検査を通す。空の連載は許容する。公開用manifestへ所有者用の内容索引や連載所属を混ぜず、本文なしの保存で記事や目録を書き換えない。既存の記事とregistryを同時に保存する経路は維持する。

ブロックエディタ・プレビュー・MDXを同階層のSVGタブとする。添削は本文に付随する作業であり、表示モードとは分ける。キーボード表示中はモバイルの下部ツールを隠し、単一のviewport hookが実caret/入力位置と固定UI、入れ子のスクロール領域を照合する。必要分のスクロールに限定し、focus・selection・compositionの本文を再設定しない。

構成パネルはグループにも本文順の番号と直下ブロック数を付ける。添削は一意に照合できた範囲を非編集中の表示に印として付け、状態は色に加えて文字とアイコンで伝える。編集DOMとMDXに差分markupを入れない。ホームから明示的に開く操作サンプルは独立した端末データとし、模擬のAI下書き・指摘であることを明記する。

## 検討した代案

- 執筆画面のメニューを増やす方法では、原稿を選ぶ前の作業と執筆中の操作の混在が残る。
- 管理用の空記事を作る方法では、不要なContentId、記事履歴、保存や公開の判定が管理操作へ混入する。
- 本文と管理で別のtaxonomyモデルを持つ方法は、サイトとCMSの互換性を損なう。既存registryと検証関数を共有する。
- `scrollIntoView`や再focusだけに頼る方法では、長い段落のcaret、複数のスクロール領域、キーボード表示後の変化を扱えず、選択範囲やIMEの継続も損ねる。
- 添削色を入力中のcontenteditableへ直接挿入すると、原文offsetと選択範囲、エディタが管理するDOMが競合する。印は読み取り用表示とパネルに限定する。

## 確認する振る舞い

ホーム初回表示・管理だけの利用で空原稿を保存しないこと、三つの開始経路、ブランチ選択と作成、公開原稿のContentId維持、戻る操作、端末での再開を確認する。管理APIでは認証、未知入力、古いhead、保存中の競合、空連載、無効参照、公開manifestへの私有情報混入を検査する。

320px/390pxのviewport試験では実際のcaret矩形と固定UIの重なりを確認し、入れ子本文・CodeMirror・管理フォームでselectionと本文の不変性を検査する。模擬のviewport/compositionイベントと実iPhoneのキーボード・日本語入力は別に受け入れる。サンプルは外部通信と保存の副作用を持たず、有効な本文・画像・四つの添削状態を返すことを確認する。
