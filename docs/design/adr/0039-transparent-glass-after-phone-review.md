# ADR 0039：実機確認後の透明なガラス表現

状態：実機のiPhoneでのフィードバック後にガラスの質感を採用（2026-10-06）。ADR 0037のガラス表面に関する判断を置き換えます。ADR 0040では、表面を変えずに周囲の導線行を調整します。

その後、[ADR 0041](0041-primary-cta-and-responsive-search.md)で配置A・16px角丸・狭幅の写真背景調整を反映しています。本記録の数値・検証は透明ガラス採用時点のものです。基になる6%白・2pxぼかし・反射の質感を保つ判断は引き続き適用します。

ユーザーは、以前のCTAを実機のiPhoneで見た際、ガラスではなく紫の塗りボタンに見えるとして却下しました。対応ブラウザー向けの以前の背景は、すでに暗くした写真の上に不透明度70%の紫を重ね、ホバー時88%、押下時90%としていました。さらに14pxのぼかしで、残っていた写真の細部も消えていました。これがCSSから確認できる具体的な原因です。却下されたiPhone実機の計算済みスタイルを遠隔で調べたわけではありません。

変更後は、白6%の背景、2pxのぼかし、控えめな彩度・明るさ調整、非対称な反射の縁を使います。左上と右下の反射、内側の縁の影、角丸でレンズの厚みを感じさせ、中央には背景の質感を残します。ホバー・押下の反応でも透明感を維持します。要素全体のopacityではなく背景色のアルファ値を使い、装飾はポインター操作を妨げません。フォーカス輪郭、48pxの操作領域、標準リンクの意味、無効状態、タッチ時のホバー制限、動きを減らす設定を維持します。未対応ブラウザー向けの不透明な代替表示も読みやすく保ちます。コピーアイコン、書体、写真配信、経路、実行時の契約は変更しません。クライアントスクリプト、常時アニメーション、ライブラリー、SVGフィルター、WebGLは追加していません。

## 互換性と光学表現の限界

[WebKitのbackdrop-filter導入説明](https://webkit.org/blog/3632/introducing-backdrop-filters/)は、合成処理と追加の描画工程を説明しています。[Safari 18](https://webkit.org/blog/15865/webkit-features-in-safari-18-0/)で接頭辞なしの構文が追加されましたが、これはSVG参照フィルターへの対応とは別です。出力されるCSSには、接頭辞付き・標準構文の両方の通常のCSS関数を残します。

[CSSWG Filter Effects Level 2草案](https://drafts.csswg.org/filter-effects-2/#BackdropRoot)では、祖先要素のopacity、filter、マスク、クリップ、合成効果が背景の参照範囲を制限し得ると説明されています。実際のCTAの祖先要素をWebKitとEdgeで調べたところ、opacityは1、filter・mask・clip-pathはnone、blend modeはnormalで、祖先にbackdrop-filterはありませんでした。写真自身のfilterはCTAの祖先ではなく、兄弟の画像要素にあります。ヒーローの重なりを分離する設定やz-indexだけを、背景の参照範囲が壊れている証拠とは扱いませんでした。

[WebKitの不具合317059](https://bugs.webkit.org/show_bug.cgi?id=317059)には、URL参照によって背景フィルター全体が無効になる場合があると報告されています。作者の[CSS/SVG屈折実験](https://kube.io/blog/liquid-glass-css-svg/)も、ブラウザーデモをChrome専用と明記しています。実験として確認しましたが、Safari対応ライブラリーとして採用したり、その実装をコピーしたりしていません。

採用したボタンとは独立した非公開の縞模様テストで、一定方向にずらす`feDisplacementMap`を試しました。同じ領域のスクリーンショットの画素はEdgeで変化し、RGBの平均絶対差は約162/255でした。WebKitでは変化せず0でした。これは実際の描画結果であり、`CSS.supports`からの推測ではありません。そのため、iPhone向けの実装ではSVGのURLフィルターを不採用としました。ランダムな乱流や重いWebGLも採用していません。

**選んだCSSは、透明感と反射・面取り風のハイライトを表現します。任意の背景画素を空間的に屈折させるものではなく、AppleのネイティブLiquid Glassでもありません。** ネイティブ風の要望に対し、ブラウザー間で使えるCSSによる近似は部分的です。WebKitの結果を本当の屈折と説明しないでください。ユーザーが候補を確認した後に求める場合、より強いブラウザー固有の表現は別途判断します。

## 検証

Playwright 1.63.0と公式WebKitビルドは、今回の作業用一時ツールディレクトリーにのみ導入しました。リポジトリーの依存関係や外部アカウントは追加していません。WindowsのWebKit 26.6とEdgeで、1487/820/390/320px、実際のCSPの条件下で確認しました。背景の低いアルファ値、機能する背景フィルター、祖先要素、写真の描画、操作領域、横にはみ出さないこと、キーボードによる実行、繰り返しの戻る・進むを検証しています。既存のEdge検証では、ホバー、フォーカス、不透明な代替表示、無効状態、動きを減らす設定も確認しています。スクリーンショットにはCTAが乗る写真の暗い領域を記録しました。字形を一時的に隠し、実際の文字背景を撮影して白い文字とのコントラストをサンプル取得したところ、確認したすべての幅で4.5:1を超えました。390pxのWebKitは約4.94:1でした。これは現在の暗くしたヒーローに限る結果で、任意の明るい背景での保証ではありません。

同じ非公開ホームの性能計測では、LCP中央値は変更前1.668s、変更後1.664s、CLSは0でした。CSSのgzip転送量は141バイト増え、画像・フォント・JSの容量は不変でした。このわずかな時間差はローカル計測の変動範囲内であり、追加の速度向上の証拠ではありません。実際のHTTP代替コピーと安全な接続でのクリップボード検証も再実行し、成功しました。

このWebKit検証は、iPhone実機やユーザーと同じSafari版での確認ではありません。その後、ユーザーは2026-10-06にボタンデザインを採用し、周囲との調和を求めました。以前の速度に対する承認は維持し、画像・フォント出力や静的ページのJSゼロを変えずに、転送量上限と同じローカルモバイル計測を再確認します。正確なコミット・CIと最終計測はPR 65および`docs/performance/glass-review-v1.json`に記録しています。
