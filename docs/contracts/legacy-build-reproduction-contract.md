# Legacy Build Reproduction Contract

## Amendment status

This document is a **post-Freeze proposed amendment** associated with ADR-0028。It is pending a fresh clean-room design audit and explicit operator acceptance。Until then, it does not change the accepted Frozen Design, the Phase 1A baseline, or the current behavior of `npm run migration:legacy:reproduce`。

## Purpose

Define what it means to reproduce an immutable legacy application when clean builds can exhibit genuine output-order nondeterminism。

Legacy build reproduction is not a claim that all generated bytes must necessarily be identical。It means the exact frozen application can be rebuilt from exact source, dependency, and toolchain identity and every observed variance is either absent or completely explained by a versioned, explicitly permitted equivalence rule。

## Profile

Initial profile ID:

```text
legacy-build-equivalence-v1
```

This profile is limited to the already-characterized legacy ordering behavior in this contract。It is not a generic normalization, filename allowlist, or ignore-differences mechanism。Unexpected variance is `FAIL` and requires another explicit design review before any profile expansion。

## Required source and toolchain identity

Every reproduction evidence set must bind:

- repository;
- annotated tag name;
- annotated tag object SHA;
- peeled commit SHA;
- `package-lock.json` Git blob SHA from that commit;
- exact Node version;
- exact npm version;
- ordered commands used for install, check, and build。

For the initial frozen snapshot:

```text
repository: Xpotato1024/xpotato-site
tag: legacy-pre-vnext-2026-08-28
tagObjectSha: 8503f5a50a5fb3d27a02422da0b50dc66c818b02
commitSha: 927d105713561309fc5e2374396f86646b5aeb2a
packageLockBlobSha: bb805f8a5558bf1eebe6d57d8292f7f69cb06d5a
observedNodeVersion: v24.19.0
observedNpmVersion: 11.19.0
```

At least two clean isolated builds from the same identity are required。Commands remain equivalent to:

```text
npm ci
npm run check
npm run build
```

The tracked frozen source must be byte-identical before and after each reproduction。The validator must not upgrade dependencies or edit legacy package metadata to obtain a pass。

## Public endpoint identity

Both clean builds must expose the exact same normalized public endpoint set。The set must also match the deterministic migration inventory route model where applicable; inventory-only query identities that are not static files are compared through their defined inventory projection, not fabricated as build files。

A missing endpoint, new endpoint, inconsistent built-file-to-endpoint mapping, or irreconcilable inventory disagreement is always `FAIL`。

The evidence stores a deterministic endpoint-path digest for each build。Equal digests alone are insufficient if extraction errors or collisions occurred。

## Non-HTML output identity

All non-HTML build artifacts must be byte-identical across the isolated builds unless a later explicitly accepted artifact-specific profile states otherwise。

For `legacy-build-equivalence-v1`, exact bytes are required for all non-HTML outputs, including as applicable:

- JavaScript;
- CSS;
- images;
- fonts;
- `robots.txt`;
- XML and sitemap outputs;
- every other static non-HTML file。

The validator must not broadly normalize, omit, or reserialize these artifacts。

## HTML comparison boundary

An HTML byte difference is not automatically accepted。Every difference must be proven to consist only of one or more permitted tie-equivalent permutations。The page shell and every region outside those proven sequences remain byte-identical; each permuted item's rendered material representation and link/target remain identical apart from sibling position。All other HTML variance is `FAIL`。

### Rendered item identity

For each compared sequence, the versioned extractor must recover a stable item identity and its rendered material representation, including its link or target identity where present。Apart from sibling placement, the compared representation must prove the same item membership and the same rendered material content/link identity。

The extractor may ignore only the position that it is actively proving as a permitted permutation。It must not erase, rewrite, or broadly normalize other item or page content。If the item boundary, identity, content, link target, or sort keys cannot be proven from bounded static evidence, comparison fails closed。

## Tie-equivalent permutation

Two output sequences are tie-equivalent only when:

1. they contain the exact same item identities;
2. each item has the same rendered material content and link/target identity;
3. items with unequal declared legacy sort keys retain the same relative ordering;
4. only items whose complete declared legacy sort-key tuple is equal may permute。

No item may disappear, appear, change target or content identity, move across a non-equal sort key, or change rendered material content。

## Approved v1 tie classes

Only the following classes are recognized by `legacy-build-equivalence-v1`。

### Published-entry ordering

Declared tuple:

```text
(pubDate DESC)
```

Items with equal `pubDate` may permute。Items with different `pubDate` may not。

### Related Blog ordering

Declared tuple:

```text
(score DESC, pubDate DESC)
```

Only items with equal `score` and equal `pubDate` may permute。

### Featured Project ordering

Declared tuple:

```text
(featuredOrder ASC with missing = MAX_SAFE_INTEGER, pubDate DESC)
```

Only items equal on both effective keys may permute。

No other class may be inferred from a newly observed difference。In particular, a list of known differing HTML filenames does not prove equivalence。

## Comparison representation is evidence only

The validator may construct a versioned comparison representation。That representation exists solely to classify two naturally generated builds and must never:

- modify legacy source;
- modify the legacy tag;
- modify either legacy dist tree;
- rewrite generated HTML;
- replace raw manifests;
- create a synthetic canonical site and present it as historical output。

Each naturally generated artifact and raw dist manifest remains preserved as observed evidence。

## Required machine evidence

Equivalent field naming is permitted, but the following semantics are required:

```ts
interface LegacyBuildReproductionEvidence {
  schemaVersion: 1;
  equivalenceProfileId: "legacy-build-equivalence-v1";
  source: {
    repository: string;
    tag: string;
    tagObjectSha: string;
    commitSha: string;
    packageLockBlobSha: string;
  };
  toolchain: {
    nodeVersion: string;
    npmVersion: string;
    buildCommands: ["npm ci", "npm run check", "npm run build"];
  };
  builds: Array<{
    rawDistManifestSha256: string;
    fileCount: number;
    endpointPathsSha256: string;
    nonHtmlManifestSha256: string;
  }>;
  result:
    | {
        status: "PASS";
        rawByteIdentical: boolean;
        equivalenceVerified: true;
        differingHtmlPaths: string[];
        permittedTiePermutationCount: number;
      }
    | {
        status: "FAIL";
        equivalenceVerified: false;
        reason: string;
        differingPaths: string[];
      };
}
```

The build array contains at least two observations。Every observed raw manifest SHA is retained。There is no synthetic single `distManifestSha256` when raw output bytes genuinely have multiple identities。

Digest inputs are deterministic and versioned:

- built paths use `/` separators and explicit locale-independent ordering;
- `rawDistManifestSha256` covers the canonical sorted `{ path, sizeBytes, sha256 }` manifest for every built file;
- `endpointPathsSha256` covers the canonical sorted exact endpoint-path set;
- `nonHtmlManifestSha256` covers the canonical sorted `{ path, sizeBytes, sha256 }` records for every non-HTML artifact;
- each digest uses the repository canonical JSON + SHA-256 rule。

`rawByteIdentical` is true only when every observed raw dist manifest identity is the same。`permittedTiePermutationCount` counts the maximal tied sequence groups whose ordering differs and whose equivalence was positively proven by the versioned extractor; it is never a count of filenames ignored。

## PASS semantics

`PASS` / `reproduced` requires all of:

- exact annotated tag object and peeled commit identity verified;
- exact lockfile blob identity verified;
- exact recorded toolchain and build commands used;
- clean `npm ci` succeeds;
- legacy check succeeds;
- legacy build succeeds;
- tracked frozen source remains unchanged;
- at least two isolated builds are observed;
- endpoint sets are exactly equal;
- the endpoint set agrees with the inventory projection;
- non-HTML artifacts are byte-identical;
- every HTML difference is completely classified as a permitted tie-equivalent permutation under `legacy-build-equivalence-v1`;
- no unexpected HTML difference remains。

Full raw dist byte equality is a stronger special case and is recorded as `rawByteIdentical = true`。It is not required when all characterized-equivalence requirements are positively proven。

## FAIL semantics

Reproduction fails on any of:

- tag, tag-object, commit, or lockfile mismatch;
- tracked source mutation;
- install, check, or build failure;
- endpoint mismatch or endpoint/inventory disagreement;
- non-HTML byte mismatch;
- HTML item membership difference;
- HTML material-content or link/target difference;
- ordering change between unequal complete sort-key tuples;
- variance outside an approved v1 tie class;
- comparison extractor ambiguity or inability to prove equivalence。

Uncertainty fails closed。A successful command exit must never be manufactured by suppressing a difference。

## Compact baseline implication

After acceptance and later implementation, a valid compact baseline may distinguish:

```yaml
reproductionStatus: PASS
rawByteIdentical: false
equivalenceVerified: true
equivalenceProfileId: legacy-build-equivalence-v1
observedRawDistManifestSha256:
  - 570f9ae9419136c5ae47ea49e0000d43b20df44e86bbd41d010bea1680d928f6
  - 235c3fe4083645eb65990a15d7c38e05579d67fde4346daedbf7d5f73cad7358
endpointPathsSha256: 3bdb9ced87a60ee4bb9d52c680b274ba1ed8438e813fd7d0c09ee5e39879fd92
nonHtmlManifestSha256: <exact digest>
differingHtmlArtifactCount: 30
permittedTiePermutationCount: <proven count>
```

These values are an example of the proposed shape, not a current PASS claim。The current machine baseline remains `FAIL` until this proposal is accepted and separately implemented with evidence。

## Non-goals

- modifying the frozen legacy source or tag;
- adding legacy tie-breakers;
- canonicalizing historical output;
- accepting arbitrary HTML nondeterminism;
- weakening route, non-HTML, content-membership, or material-content checks;
- authorizing migration, cutover, provider mutation, or deployment。
